# Lune 普及戦略 — 「多くの人に親しんでもらう」ために

Version: 2026-07-20 initial
Related: `LANGUAGE_SPEC.md`, `LANGUAGE_FUTURE_SPEC.md`, `ERROR_DIAGNOSTICS_SPEC.md`, `TUTORIAL.md`

この文書は、Lune を「多くの人に親しんでもらう」ための方向付けを分析し、施策の優先順位を定める。2026-07-20 に決めた「コンパイラが教える (the compiler that teaches)」路線を、普及戦略として具体化したものである。

## 1. Lune に入っている「新しい概念」の棚卸し

Lune は直近10年の PL 研究・言語 UX 研究の成果を小さな言語に凝縮した構成になっている。

| Lune の機能 | 研究・実務上の系譜 |
| --- | --- |
| 網羅性検査+反例 (witness) 提示 (TYP0007) | OCaml/Rust の網羅性検査。反例を診断に出すのは比較的新しい実装水準 |
| フロー依存の null 安全 (`T?`, `?.`, `??`, 条件 narrowing) | Kotlin/TypeScript 系の flow typing |
| 期待型伝播による局所型推論 (TYP0010/0011) | bidirectional typing の実用形 |
| 全診断コードに教材的解説 (`lune explain`) | Rust の `--explain`/error index の発展形。「全コードに解説がある」ことをテストで強制しているのは独自性が高い |
| did-you-mean + `lune fix` (機械適用可能な修正) | Rust の rustfix、LSP の code action 系譜 |
| 正準フォーマッタ `lune fmt` (冪等性・意味保存を再パースで検証) | gofmt 以降の「議論を終わらせるフォーマッタ」文化 |
| デフォルト遅延+明示的 strict (`strict`/`seq`/`force`) | Haskell の遅延評価を「観察可能・opt-out 可能」に再設計 |

この組み合わせは偶然ではなく一つの軸に収束している: **コンパイラが学習者に教える**。

## 2. 「多くの人に」の現実 — 新言語の採用経路は3つ

汎用言語としての普及競争 (エコシステム・ライブラリ・求人) は、個人開発の言語には構造的に勝ち目がない。現実的な入口は次の3つで、Lune の資産は (a) と (c) に強く適合する。

- **(a) 教育**: 講義・独習で「概念を学ぶための言語」として使われる (Racket、Pyret、Hedy の経路)
- **(b) ホビイスト/言語愛好家**: 面白い言語として遊ばれる (Gleam 初期、Zig 初期)
- **(c) 研究コミュニティ**: 論文・実装として引用される

## 3. ポジション: 「エラーが教材になる、日本語話者のための関数型入門言語」

競合状況にはっきりした空白がある。

- **Haskell**: 遅延評価の本家だがエラーメッセージが初学者に敵対的
- **Elm**: friendly errors の元祖だがフロントエンド専用で、概念教育には範囲が狭い
- **Racket/Pyret**: 教育言語として確立しているが S 式系/英語圏中心
- **Hedy**: 多言語化 (母語でエラーが読める) で成功したが、対象は初等教育・手続き型

「**ML 系の型・ADT・パターンマッチ・遅延評価を、母語で教えてくれるコンパイラで学ぶ**」という位置は空いている。チュートリアルが日本語で、遅延評価を第2〜6章で段階的に教える構成であることも、この位置取りを裏付ける。

キャッチコピー案: *the functional language whose compiler teaches you* / 「コンパイラが教えてくれる関数型言語」

## 4. 施策の優先順位 (インパクト × コスト)

### A. ブラウザ Playground (最優先・効果最大)

新言語の最大の離脱点はインストールである。実装が Pure Python であることは、**Pyodide (ブラウザ内 Python) でそのまま動かせる**ため普及上の武器になる。URL 一つで REPL+`explain`+診断表示が動けば「親しんでもらう」コストがゼロになる。あわせて `pip install` / `uvx lune` での配布も低コストで可能。

技術検証 PoC は `playground/` にある (検証結果は `playground/README.md`)。

### B. 診断メッセージの日本語化 (差別化の核)

`explanations.py` は全診断コードのカタログ構造を既に持つため、`--lang ja` は設計変更なしで載る。「エラーも解説も母語で読める関数型言語」は Hedy が初等教育で証明した効果を関数型教育に持ち込むもので、研究的新規性 (施策 D) と普及施策が同じ作業で手に入る。費用対効果が最も高い一手。

### C. エラー駆動学習への再編

チュートリアルに「わざとエラーを起こす → 診断を読む → `explain` で理解する → `fix` で直す」という節を組み込み、診断カタログ (全コードの解説) を Web で公開する (Rust error index 相当)。「診断こそが教材」という主張を製品自体で示す。

### D. 研究発信という増幅器

講義や演習で小規模に使って学習効果を測れば、SPLASH-E・ITiCSE、国内なら PPL・情処 PRO に出せる題材になる。「全診断に教材解説をテストで強制する設計」「witness 付き網羅性診断の教育効果」は発表価値がある。論文・発表は教育言語にとって最良の広報チャネルでもある (Hedy・Pyret が実例)。

### E. 見せ方の整備 (低コスト)

README は現在「実装済み機能の羅列」で、初見の人に物語が伝わらない。「コンパイラが教える関数型言語」を冒頭に置き、エラー表示のスクリーンショットを最初に見せる構成へ。公開を強く意識する段階になったら、リポジトリ名を `lune-lang` 等へ変える選択肢もある (GitHub はリネーム後も旧 URL をリダイレクトする)。

## 5. やらないこと

`LANGUAGE_FUTURE_SPEC.md` の Phase 2〜4 (JVM 連携・OO・実用化) は、この戦略では**当面凍結**する。Java 相互運用は「実務採用」を狙う施策だが、それは勝ち目の薄い戦線であり、教育ニッチには Python インタプリタの速度で十分。性能最適化・パッケージ管理も優先度を下げる。

言語設計上の注意が一点: デフォルト遅延は初学者には罠にもなり得る。「隠す」のではなく、評価のタイミングを観察できる道具 (REPL での thunk 可視化、`:trace` 的な機能) で「評価戦略を学べる教材」に転化するのが、教育ポジションと一貫した解き方である。

## 6. 検証方法

「親しんでもらえたか」は GitHub スター数より次で測る。

- Playground の到達数と滞在、チュートリアル完走率
- 講義で使った際の理解度・つまずき箇所 (そのまま論文のデータになる)
- `explain` がどのコードで参照されるかの分布 (匿名で取れれば診断改善の優先順位になる)

## 7. 要約

汎用普及は狙わず、「**母語で教えてくれるコンパイラを持つ関数型入門言語**」に集中する。次の一手は (1) Pyodide Playground、(2) 診断の日本語化、(3) エラー駆動チュートリアル。研究発表を広報チャネルとして使い、JVM/OO 路線は凍結する。
