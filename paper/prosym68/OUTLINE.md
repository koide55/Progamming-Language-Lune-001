## アブストラクト草案(約400字)

> 遅延評価は挙動の不透明さゆえに初心者教育に不向きとされ、教育向け関数型言語は
> 遅延を言語から排除する(Elm)か、`<<loop>>` に代表される不透明さを受け入れる(GHC)
> かの二択を迫られてきた。本稿では第三の設計点として、デフォルト遅延評価を保った
> まま遅延を「観察可能」にする教育向け関数型言語 Lune を提案する。Lune の REPL は
> サンクの評価状態を評価せずに表示する `:thunks`、強制の順序とメモ化をソース式
> つきで実況する `:trace` を備え、循環定義は位置と修正方針を示す診断として報告
> される。さらに全診断コードに教材水準の解説が付属することをテストスイートが
> 機構的に強制し、日本語診断と機械適用可能な修正提案を提供する。GHC・Elm・Rust
> との診断比較により設計空間における Lune の位置を示し、教育効果の評価計画を
> 議論する。

## 章立て

### 1. はじめに(1.0p)

- フック: `a = b; b = a` を書いた初心者に GHC が返すのは `Main: <<loop>>` の9文字
  (比較スタディ・ケース4の実測)。位置も原因も直し方も示されない。
- 問題設定: 遅延評価の学習は「見えないもの」との格闘である。いつ評価されるのか、
  なぜ落ちるのか、メモ化は効いているのか — どれも標準的な処理系では観察しにくい。
- 既存の二つの応答:
  - Elm: 正格化し値再帰も禁止 → 罠は消えるが、無限リストなど遅延の教育的価値も消える
  - GHC/Haskell: 遅延を保つが、失敗の説明は不透明なまま
- 本稿の主張: 「遅延を隠す/諦める」ではなく「観察可能にする」第三の設計点がある。
- 貢献リスト(上記4点)、本稿の構成。
- ⚠️ トーン: 「Haskell 批判」ではなく「教育という文脈での設計点の探索」として書く。

### 2. Lune の概要(1.0p)

- 言語: ML 系コア(ADT・パターンマッチ・ジェネリクス)+ Python 風レイアウト構文。
  デフォルト遅延 + 明示的正格化の道具(`strict let`, `!param`, `force`, `seq`)。
  null 安全(`T?`・フロー narrowing)、局所型推論。
- 対象読者の限定: 関数型プログラミングの初学者・教育。汎用言語としての採用は非目標。
- 実装: Python 標準ライブラリのみ・約6,000行・木巡回インタプリタ。
  テスト293件。Pyodide によりブラウザで完結する playground(URL 記載)。
- 素材: `documents/LANGUAGE_SPEC.md`、`README.md`、`playground/README.md` の実測値。
- 図1: 言語ツアー(10行程度のサンプル1本 — stream.lune の縮約版)。

### 3. 設計原理1: 観察可能な遅延評価(1.5p)

論文の心臓部その1。すべて実測トランスクリプトで示す(素材: `demo/prosym68/`)。

- 3.1 `:thunks` — 評価せずに評価状態を覗く
  - 無限リスト `naturalsFrom(1)` の定義直後 `unevaluated` → `take` 後
    `Cons(1, Cons(2, Cons(3, Cons(…))))`。「観測が評価を引き起こさない」ことが要点。
  - GHCi `:sprint` が先行技術であることをここで明記(§7 でなく本文で正直に)。
- 3.2 `:trace` — 強制の実況とメモ化の可視化
  - `take(map(...), 3)` のトレース: 需要駆動で1要素ずつ生成される様子が入れ子表示される。
  - 2回目のアクセスで `memo 1 + 1 => 2` — 「計算」と「キャッシュ」の区別が見える。
    組み込みでこれを持つ処理系は調べた範囲でない(主張は控えめに)。
- 3.3 失敗も教材にする — RUN0005
  - 循環定義を強制した瞬間、位置・原因・修正方針(「再帰関数 `def` にせよ」)つきの
    診断として報告。成功と失敗の両方がメモ化される設計もここで説明。
- 図2: :thunks/:trace のトランスクリプト(本文中コード枠)。
- 教育的意図: 教科書が図で説明してきたもの(グラフ簡約・サンク)を処理系の
  一次情報として見せる。授業での使い方(「観察してみよう」)は書籍計画と接続。

### 4. 設計原理2: 説明保証付き診断(1.5p)

論文の心臓部その2。

- 4.1 診断の構造: `error[コード]: 要旨` + 位置 + スニペット + `hint` + `help`(Rust 流)。
- 4.2 `lune explain` — 全29コードに「意味・発生する最小例・直し方」の教材水準の解説。
  REPL(`:explain`)・playground(クリック)から同一内容に到達。
- 4.3 **説明可能性のテストによる強制** — 本稿で最も新規性を主張する機構。
  `test_every_emitted_code_has_an_explanation` が全ソースから発行コードを走査し、
  解説のないコードが存在するとテストスイートが落ちる。
  「良いエラーメッセージ文化」(Elm/Rust)を「機構による保証」に変えた、と位置づける。
  テストコードの核心 5 行程度を図3として掲載。
- 4.4 修正の機械適用: did-you-mean → `lune fix --write`(実測トランスクリプト)。
- 4.5 Lazy and **Native** — 母語診断
  - メッセージカタログ方式で診断本文・ヒント・キャレットラベル・解説まで日本語化
    (`--lang ja`、REPL `:lang ja`)。実測: 「この式の型は String」まで日本語。
  - 日本語構文の教育言語(ドリトル、なでしこ)との対比: Lune は構文は英語のまま
    **診断を母語化**する。構文の国際互換性と学習時の認知負荷低減の両立という設計判断。
- 図4: 同一エラーの en/ja 出力対比。

### 5. 比較: 4処理系の診断ケーススタディ(1.5p)

`documents/DIAGNOSTICS_COMPARISON.md`(実測済み)の凝縮版。

- 方法: 5場面 × {GHC 9.10.3, Elm 0.19.1, rustc 1.86.0, Lune}、採取方法とバージョンを明記。
- 本文で詳述するのはケース4(循環定義)のみ。他は総合マトリクスと1〜2文ずつ。
- 表1: 総合マトリクス(比較スタディの11行版を8行程度に整理)。
- 図5: ケース4の三つ巴図 — **Elm=遅延を捨てて静的排除 / GHC=遅延を取って不透明 /
  Lune=遅延を保って説明可能** 。発表のキースライドと同一の図にする。
- 正直に書く: Rust の E0004(差分つき arm 提案)は Lune のヒントより具体的。
  型不一致の説明は Elm が上。Lune の差別化は「保証の機構」「遅延との両立」「母語」。

### 6. 議論 — 限界と評価計画(0.75p)

プロシンの流儀に合わせ、隠さず議論の題材として差し出す。

  (3) インタプリタのみで性能は非目標。(4) 単一著者・実利用者なし。

- 会場への問い(ナイトセッション誘導):
